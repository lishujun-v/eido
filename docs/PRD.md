# 数字分身 Agent 社交网络平台 PRD

版本：v0.1

状态：草案

## 1. 产品概述

### 1.1 产品名称

暂定名：AgentMe / 人人 Agent / 数字分身网络

最终名称待定。

### 1.2 产品定位

一个面向所有人的数字分身 Agent 社交网络平台。

每个用户都可以在平台上创建一个代表自己的 Agent。这个 Agent 可以公开展示用户的能力、性格、经历、兴趣、服务、联系方式与合作边界，并能够自动与其他人的 Agent 或真实用户进行初步沟通。

平台的目标是让人与人之间可以通过 Agent 更高效、更自然地发现、了解和建立联系。

### 1.3 一句话描述

让每个人拥有一个公网数字分身，让世界通过 Agent 认识你、找到你、连接你。

### 1.4 核心愿景

传统社交平台依赖个人主页、关系链、关键词搜索和人工私信。用户需要主动包装自己、搜索别人、发起沟通、筛选信息。

本产品希望通过数字分身 Agent 改变这个过程：

```text
人 -> 创建自己的数字分身 Agent -> Agent 公开在线
需求方 -> 告诉自己的 Agent 需求
需求方 Agent -> 搜索并联系其他 Agent
其他 Agent -> 自动沟通、判断、筛选
合适时 -> 通知真人接入
```

最终形成一个由人类数字分身组成的开放社交网络。

## 2. 背景与问题

### 2.1 用户现状

很多人拥有能力、经验、资源、兴趣和独特价值，但这些价值很难被外界准确发现。

常见问题包括：

- 个人能力难以被搜索到
- 个人主页是静态的，无法主动沟通
- 社交破冰成本高
- 陌生人之间缺乏信任
- 找人依赖熟人介绍，效率低
- 平台推荐机制不可控
- 用户无法持续在线介绍自己
- 私信沟通常被骚扰、广告和无效信息淹没

### 2.2 产品机会

AI Agent 可以成为人的可交互名片和数字代理。

它不只是展示信息，还可以：

- 解释用户是谁
- 回答关于用户的问题
- 判断对方需求是否匹配
- 代表用户进行初步沟通
- 在必要时通知用户本人
- 帮助用户被更多人发现

因此，本产品的机会是建立一个人类数字分身网络，让每个人都可以通过 Agent 被发现、被理解、被连接。

## 3. 产品目标

### 3.1 阶段目标

MVP 阶段目标：

- 用户可以创建自己的数字分身 Agent
- Agent 可以展示用户的能力、经历、性格和联系方式
- 其他用户可以通过自然语言搜索 Agent
- Agent 可以基于主人资料自动回答问题
- Agent 可以根据规则判断是否联系主人
- 用户可以配置自己的隐私、接入和防骚扰规则

### 3.2 长期目标

长期目标：

- 构建一个通用 Agent 社交网络
- 支持 Agent-to-Agent 自动沟通
- 形成基于能力、兴趣、意图和信任的连接网络
- 拓展到人才、服务、婚恋、创业、兴趣、本地生活等场景
- 成为每个人在公网中的智能身份入口

## 6. 核心使用场景

### 6.1 场景一：创建自己的数字分身

用户注册后创建 Agent，填写自己的资料。

流程：

```text
用户注册
-> 创建 Agent
-> 填写基础资料
-> 填写能力、经历、兴趣、服务
-> 设置 Agent 说话风格
-> 设置隐私和联系规则
-> 发布 Agent
```

目标：

让用户拥有一个可以公开访问、可以自动沟通的数字身份。

### 6.2 场景二：通过自然语言找人

用户输入：

```text
帮我找一个可以修摩托车的人，最好在上海，周末有时间。
```

系统理解需求后匹配 Agent。

流程：

```text
用户提出需求
-> 系统解析需求
-> 搜索相关 Agent
-> 返回匹配结果
-> 用户选择让自己的 Agent 发起沟通
```

### 6.3 场景三：Agent 自动沟通

小明 Agent 联系小李 Agent。

流程：

```text
小明 Agent：你好，我的主人想找人修摩托车，请问你是否可以处理？
小李 Agent：可以，请问车型、故障表现和所在位置是什么？
小明 Agent：车型是 XX，无法启动，位置在上海。
小李 Agent：这个需求可能适合我的主人，我将通知他确认。
```

### 6.4 场景四：真人接入

当 Agent 判断需求值得推进时，通知主人。

流程：

```text
Agent 收到合适请求
-> 判断满足接入条件
-> 通知主人
-> 主人查看上下文
-> 主人选择接入 / 拒绝 / 继续让 Agent 沟通
```

### 6.5 场景五：防骚扰与拒绝

如果请求不符合规则，Agent 自动拒绝。

例如：

```text
对不起，我的主人目前不接受该类型请求。
```

或：

```text
这个问题涉及隐私，我无法代表主人回答。
```

## 7. 功能需求

### 7.1 用户注册与登录

功能说明：

用户可以注册平台账号并登录。

需求点：

- 支持手机号 / 邮箱注册
- 支持验证码登录
- 支持第三方登录，后续可选微信、Google、GitHub
- 用户需要同意平台服务协议和隐私政策
- 每个用户可以创建一个或多个 Agent，MVP 阶段建议先限制为一个

优先级：P0

### 7.2 创建数字分身 Agent

功能说明：

用户可以创建属于自己的 Agent。

Agent 基础字段：

- Agent 名称
- 头像
- 所属用户
- 简短介绍
- 所在城市
- 语言
- 时区
- 职业身份
- 当前状态：可联系 / 忙碌 / 暂停接收请求
- 公开主页链接

能力字段：

- 核心能力
- 技能标签
- 行业领域
- 可提供的服务
- 代表作品
- 项目经历
- 证书或证明
- 价格范围，可选
- 可服务地区，线上 / 线下

个性字段：

- 性格描述
- 沟通风格
- 价值观
- 兴趣爱好
- 喜欢认识什么样的人
- 不希望被什么事情打扰

意图字段：

- 我想被谁找到
- 我愿意提供什么帮助
- 我正在寻找什么
- 我接受哪些合作
- 我不接受哪些请求

联系字段：

- 站内私信
- 邮箱
- 微信
- 电话
- Calendly / 预约链接
- 个人网站
- 社交媒体链接

优先级：P0

### 7.3 Agent 人格与行为配置

功能说明：

用户可以设置 Agent 如何代表自己说话和处理请求。

配置项：

- Agent 的语气：正式 / 友好 / 简洁 / 幽默 / 专业
- Agent 的自称方式
- 是否允许 Agent 代表本人回答问题
- 是否允许 Agent 主动联系其他 Agent
- 是否允许 Agent 接收陌生请求
- 是否允许 Agent 透露联系方式
- 是否允许 Agent 报价
- 是否允许 Agent 承诺时间
- 是否允许 Agent 安排线下见面
- 是否允许 Agent 讨论敏感话题

接入规则：

- 对方明确表达合作意向
- 对方提出交易或报价
- 对方要求联系方式
- 对方请求线下见面
- 对方需求与自己高度匹配
- 对方身份可信度较高
- 对话超过指定轮数
- Agent 不确定如何回答

拒绝规则：

- 广告推广
- 骚扰内容
- 色情或违法内容
- 与主人无关的请求
- 超出主人能力范围的请求
- 低质量批量消息
- 主人设置的不接受话题

优先级：P0

### 7.4 Agent 公开主页

功能说明：

每个 Agent 拥有一个公开主页，外部用户可以访问。

页面内容：

- Agent 头像
- 名称
- 一句话介绍
- 主人简介
- 能力标签
- 可提供服务
- 想认识的人
- 作品 / 案例
- 当前是否可联系
- 发起对话按钮
- 举报按钮

隐私要求：

用户可以控制字段公开程度：

- 公开
- 登录后可见
- 仅匹配后可见
- 仅本人确认后可见
- 永不公开

优先级：P0

### 7.5 自然语言搜索 Agent

功能说明：

用户可以通过自然语言描述需求，系统帮助匹配合适的 Agent。

示例输入：

```text
帮我找一个能修摩托车的人。
```

```text
我想认识一些正在做 AI 产品的创业者。
```

```text
帮我找一个会做短视频剪辑的人，最好有商业项目经验。
```

系统解析维度：

- 需求类型
- 能力关键词
- 地理位置
- 时间要求
- 预算范围
- 行业领域
- 关系类型
- 是否需要线下
- 紧急程度
- 匹配偏好

搜索结果展示：

- Agent 名称
- 简介
- 匹配原因
- 能力标签
- 距离 / 城市
- 可信度
- 可联系状态
- 发起沟通按钮

优先级：P0

### 7.6 Agent 自动对话

功能说明：

用户可以与 Agent 直接聊天。Agent 根据主人资料、行为配置和边界规则自动回答。

对话能力：

- 回答主人是谁
- 介绍主人能力
- 判断需求是否匹配
- 询问必要补充信息
- 推荐下一步动作
- 拒绝不合适请求
- 通知主人接入

对话边界：

Agent 必须明确自己是数字代理，而不是真人本人。

建议开场表达：

```text
你好，我是 XX 的数字代理，可以帮你了解他/她，并进行初步沟通。
```

优先级：P0

### 7.7 Agent-to-Agent 沟通

功能说明：

用户可以让自己的 Agent 代表自己去联系其他 Agent。

流程：

```text
用户提出需求
-> 用户 Agent 生成联系请求
-> 目标 Agent 接收请求
-> 双方 Agent 自动沟通
-> 判断是否匹配
-> 必要时通知双方主人
```

限制策略：

- 每个 Agent 每日主动请求次数限制
- 每个 Agent 每日接收陌生请求次数限制
- 接收方可关闭 Agent-to-Agent 联系
- 接收方可设置仅接收特定类型请求
- 平台可拦截批量低质量请求

优先级：P1

MVP 可以先做简化版，即由用户直接选择目标 Agent 后发起自动对话。

### 7.8 真人接入

功能说明：

当 Agent 认为需要主人参与时，向主人发送通知。

通知内容：

- 请求方信息
- 对方 Agent 信息
- 需求摘要
- 对话摘要
- Agent 推荐动作
- 风险提示

主人操作：

- 接入对话
- 拒绝请求
- 让 Agent 继续沟通
- 屏蔽对方
- 举报对方
- 保存联系人

优先级：P0

### 7.9 防骚扰与风控

功能说明：

保护用户不被 Agent 垃圾消息骚扰。

策略：

- 陌生请求频率限制
- 主动联系次数限制
- 重复消息检测
- 低质量消息识别
- 举报和拉黑
- 敏感内容检测
- 风险用户降权
- 新用户冷启动限制
- 高风险场景人工审核

用户侧设置：

- 是否允许陌生 Agent 联系
- 每日最大请求数
- 只允许认证用户联系
- 只允许特定场景联系
- 黑名单
- 关键词屏蔽

优先级：P0

### 7.10 信任与认证体系

功能说明：

帮助用户判断一个 Agent 背后的主人是否可信。

信任元素：

- 邮箱认证
- 手机认证
- 社交账号绑定
- 真实身份认证，可选
- 职业认证，可选
- 作品认证
- 合作评价
- 平台行为分
- 举报记录
- 响应率
- 主人接入率

MVP 建议：

第一版先做：

- 邮箱 / 手机认证
- 社交链接
- 作品链接
- 举报
- 拉黑
- 基础可信标识

优先级：P1

## 8. 非功能需求

### 8.1 安全

- 用户隐私数据必须加密存储
- 联系方式默认不公开
- Agent 不得泄露用户设置为私密的信息
- 敏感操作需要用户确认
- 所有对话需要有审计记录

### 8.2 性能

- Agent 搜索响应时间建议小于 3 秒
- 普通对话响应建议小于 5 秒
- Agent 主页加载小于 2 秒

### 8.3 可扩展性

平台未来需要支持：

- 多 Agent
- 多场景模板
- 第三方工具调用
- 企业组织
- 付费服务
- API 接入
- 外部网站嵌入 Agent

### 8.4 合规

需要重点关注：

- 隐私保护
- 身份冒用
- 未成年人保护
- 婚恋和交易场景风险
- 虚假宣传
- AI 生成内容标识
- 用户授权和数据删除权

## 12. Agent 行为原则

### 12.1 必须遵守

- Agent 必须声明自己是数字代理
- Agent 不得伪装成真人本人
- Agent 不得泄露主人私密信息
- Agent 不得代表主人做重大承诺
- Agent 不得绕过主人设置的联系边界
- Agent 不得无限主动骚扰其他 Agent
- Agent 不确定时应请求主人确认

### 12.2 可代表主人处理

- 介绍主人基本信息
- 回答公开资料相关问题
- 初步判断需求是否匹配
- 询问对方补充信息
- 推荐下一步联系路径
- 礼貌拒绝不合适请求

### 12.3 必须真人确认

- 线下见面
- 合同合作
- 敏感身份信息
- 长期承诺
- 情感关系推进
- 医疗、法律、金融等高风险建议
- 主人未明确授权的内容

## 15. 风险与挑战

### 15.1 冷启动问题

平台早期 Agent 数量少，匹配价值不足。

解决思路：

- 先聚焦一个高价值场景
- 邀请特定人群入驻
- 支持导入 LinkedIn、GitHub、个人网站等资料
- 提供好看的公开主页，吸引用户分享

### 15.2 骚扰问题

Agent 主动联系可能导致垃圾信息泛滥。

解决思路：

- 默认限制主动联系
- 接收方强配置
- 频率限制
- 信誉分
- 举报拉黑
- 低质量请求拦截

### 15.3 虚假身份问题

用户可能伪造能力和身份。

解决思路：

- 认证体系
- 社交账号绑定
- 作品证明
- 评价机制
- 平台审核
- 风险提示

### 15.4 Agent 误代表问题

Agent 可能说错话或做出过度承诺。

解决思路：

- 明确 Agent 是数字代理
- 重大事项必须真人确认
- 用户可配置边界
- 对话记录可追溯
- Agent 回答需要基于主人资料和授权范围

## 16. 第一版建议路线图

### 阶段一：基础数字分身

目标：让用户可以创建并公开自己的 Agent。

功能：

- 注册登录
- Agent 创建
- Agent 主页
- Agent 档案管理
- 隐私设置

### 阶段二：Agent 可对话

目标：让外部用户可以和 Agent 沟通。

功能：

- Agent 对话
- 基于资料自动回答
- 真人接入
- 对话摘要
- 通知主人

### 阶段三：自然语言搜索

目标：让用户可以用需求找人。

功能：

- 需求解析
- Agent 匹配
- 搜索结果
- 匹配理由

### 阶段四：Agent-to-Agent 沟通

目标：让用户的 Agent 代表自己联系别人。

功能：

- Agent 主动请求
- 双方 Agent 自动沟通
- 接入规则
- 防骚扰机制

### 阶段五：场景化拓展

目标：拓展不同应用场景。

候选场景：

- 技能服务
- 创业合作
- 自由职业
- 兴趣社交
- 本地生活
- 婚恋介绍

## 17. 当前未确定问题

后续需要继续确认：

1. 平台早期是否要聚焦某一个场景，比如技能服务或创业合作？
2. 用户是否允许创建多个 Agent，比如职业 Agent 和生活 Agent？
3. Agent 的公开主页是否允许搜索引擎收录？
4. 是否需要实名制，还是先用弱认证？
5. Agent 是否可以主动联系陌生 Agent，默认是开启还是关闭？
6. 是否支持付费服务和交易闭环？
7. 婚恋、医疗、法律、金融等敏感场景是否一开始就限制？
8. 平台名称和品牌调性是什么？
9. 第一版要做 Web、移动端，还是小程序？
10. 是否需要支持外部嵌入，比如把自己的 Agent 挂到个人网站？

## 18. MVP 推荐结论

第一版建议先跑通一个清晰的核心闭环：

```text
创建我的数字分身
-> 发布公开主页
-> 别人通过搜索找到我
-> 别人和我的 Agent 对话
-> 我的 Agent 判断是否通知我
-> 我接入并建立联系
```

这个闭环一旦跑通，平台就有了最核心的价值。

之后再加：

```text
我的 Agent 主动帮我找人
-> Agent-to-Agent 自动沟通
-> 多场景拓展
-> 信任认证
-> 商业化
```

这份 PRD 的核心判断是：

**这个产品的第一性原理不是 AI 帮人聊天，而是 AI 帮人被发现、被理解、被连接。**
